# Бизнес-логика модуля marketplace

Документ описывает **прикладную бизнес-логику сервиса `marketplace`**: B2B для сторонних клиник, white-label, роли, сценарии записи и правила для backend на `Go`.

Связанные планы:

- backend: [`../backend/implementation-plan.md`](../backend/implementation-plan.md)
- frontend: [`../frontend/implementation-plan.md`](../frontend/implementation-plan.md)
- индекс marketplace: [`../README.md`](../README.md)

---

## Назначение

Фокус:

- B2B-модель для сторонних клиник
- white-label витрина каждой клиники
- роли и границы доступа
- сценарии записи для анонимного и авторизованного пользователя
- правила, которые backend на `Go` должен enforce-ить на сервисном слое

## 1. Продуктовая модель

`marketplace` — это не одна клиника, а платформа для **нескольких сторонних клиник**.

Из этого следуют базовые правила:

- каждая клиника живет в своем scope
- сотрудники одной клиники не должны видеть админские данные другой клиники
- публичная витрина клиники должна быть настраиваемой
- единый `frontend/` обслуживает несколько витрин как white-label клиент
- backend `marketplace` хранит и бизнес-данные, и конфигурацию публичного представления клиники

## 2. White-label модель фронта

Хотя код фронта у нас единый, для бизнеса это должно выглядеть как "у каждой клиники свой фронт".

На практике это означает:

- у клиники есть `clinic_slug`
- опционально у клиники есть свой домен
- у клиники есть theme / branding config
- у клиники есть набор публичных настроек: тексты, баннеры, SEO, контакты, включенные блоки

Что клиника должна уметь менять:

- логотип
- название
- цвета и визуальную тему
- публичные тексты и блоки
- контакты
- список отображаемых филиалов
- публикацию специалистов и услуг на витрине

Важно:

- white-label влияет на внешний вид и контент
- white-label не должен ломать общую бизнес-логику записи
- правила слотов, доступов и статусов должны оставаться едиными для платформы

## 3. Основные роли

### `platform_admin`

Полный доступ к платформе.

Нужен для:

- управления всеми клиниками
- просмотра системных настроек
- кросс-клиничных операций поддержки

### `clinic_admin`

Администратор конкретной клиники.

Может:

- управлять специалистами своей клиники
- управлять услугами своей клиники
- управлять расписанием своей клиники
- управлять white-label настройками своей витрины
- просматривать и редактировать записи своей клиники

Не может:

- получать доступ к данным другой клиники
- управлять глобальными платформенными настройками

### `doctor`

Врач конкретной клиники.

Может:

- видеть свое расписание
- видеть свои записи
- смотреть, кто записан и во сколько
- при необходимости фильтровать свободные окна

Не может:

- управлять всей клиникой
- менять настройки витрины
- видеть чужие записи без отдельного разрешения

### `call_center_manager`

Оператор записи / менеджер call-центра.

Может:

- искать пациента
- создавать запись пользователю
- выбирать клинику, специалиста и слот в рамках своего scope
- просматривать свои и доступные ему записи

### `sales_manager`

Продажники платформы или сети клиник.

Могут:

- видеть записи пользователей
- видеть, кто куда записался
- записывать пользователя в любую доступную им клинику
- в будущем работать с отзывами, рассылками и звонками

Эта роль должна быть отдельной от `clinic_admin`, потому что ее зона ответственности кросс-клиничная и ближе к продажам, чем к локальному администрированию клиники.

### `patient`

Пользователь-пациент.

Может:

- смотреть специалистов
- смотреть страницы специалиста
- смотреть свободное время
- создавать запись
- видеть свои записи, если авторизован

## 4. Scoped access

### Почему не стоит хранить только `admin.someClinic`

Формат permission вроде `admin.someClinic` понятен бизнесу, но как единственная модель он плохо масштабируется.

Проблемы:

- permissions начнут плодиться по числу клиник
- трудно переиспользовать роли на филиалы и сети клиник
- неудобно писать SQL и JWT claims

### Рекомендуемая backend-модель

Хранить:

- `role_code`
- `scope_type`
- `scope_id`
- `scope_code`

Пример:

- `role_code = clinic_admin`
- `scope_type = clinic`
- `scope_id = <uuid clinic>`
- `scope_code = someClinic`

А уже для UI, логов и отладки можно строить alias:

- `admin.someClinic`

То есть:

- для бизнеса и интерфейса можно показывать `admin.<clinic_code>`
- для БД и backend-логики источником истины должна быть роль + scope

## 5. Клиентский сценарий записи

### Неавторизованный пользователь

Неавторизованный пользователь может:

- просматривать врачей
- открывать страницу специалиста
- смотреть график
- выбирать свободное время
- создавать запись

Но перед созданием записи он обязан заполнить форму:

- имя
- фамилия
- возраст
- номер телефона

Опционально позже можно добавить:

- email
- согласие на обработку данных
- комментарий к записи

### Авторизованный пользователь

Авторизованный пользователь не должен повторно вводить данные, которые уже есть в системе.

Правило:

- если нужные данные уже есть, форма записи сразу идет к подтверждению
- если часть обязательных данных отсутствует, фронтенд должен дозапросить только недостающие поля

Обязательное поле для авторизованного пользователя:

- `ИИН`

Если у пользователя нет `ИИН`, перед завершением записи система должна:

1. показать шаг дозаполнения профиля
2. сохранить недостающее поле
3. только потом завершить создание записи

## 6. Поведение врача

Врач должен иметь отдельный кабинет.

В нем должны быть:

- свое расписание
- список своих записей
- календарное представление записей
- информация, кто записан и во сколько

Опционально:

- фильтр "показывать только свободные окна"
- фильтр по филиалу, если врач работает в нескольких филиалах

## 7. Поведение администратора клиники

Админ клиники должен видеть только свою зону ответственности.

Он управляет:

- специалистами
- услугами
- расписанием
- слотами
- публичной витриной клиники
- записями своей клиники

Он не должен:

- просматривать админку другой клиники
- работать с системными ролями платформы
- иметь права `platform_admin`

## 8. Поведение call-центра

Менеджер call-центра работает как оператор записи.

Его основная ценность:

- помочь пациенту подобрать слот
- создать запись от имени пациента
- быстро работать с расписанием и поиском специалиста

С точки зрения backend это отдельный сценарий создания записи, но не отдельная доменная модель.

## 9. Поведение sales

Sales работает не как локальный админ клиники, а как роль поверх записей и лидов.

Базовый scope для начала:

- видеть записи пользователей
- видеть, в какую клинику и к кому они записаны
- создавать запись в любую доступную клинику

На следующих этапах сюда же могут добавиться:

- отзывы
- сегментация пользователей
- рассылки
- звонки
- повторные предложения и retention-механики

## 10. Правила, которые backend обязан enforce-ить

- запись создается только в свободный слот
- слот принадлежит нужному специалисту и клинике
- анонимная запись невозможна без обязательной формы пациента
- авторизованная запись невозможна без обязательных недостающих полей
- для авторизованного пользователя `ИИН` обязателен
- админ клиники ограничен своим `clinic scope`
- врач ограничен своими записями и расписанием
- sales и call-центр работают только в рамках выданного scope
- white-label настройки не дают доступ к данным другой клиники

## 11. Что это означает для схемы БД

Минимально нужно заложить:

- `clinic_frontend_configs`
- `clinic_domains`
- `clinic_members`
- `clinic_member_roles`
- `patient_refs` с полями для snapshot данных пациента
- `appointments` со snapshot данных записи

Для пациента в snapshot стоит хранить:

- имя
- фамилию
- возраст
- телефон
- `ИИН`, если он обязателен по сценарию

## 12. Что это означает для API

Нужно разделить контуры:

- публичный API витрины
- API записи
- API администратора клиники
- API врача
- API call-центра
- API sales

Это важнее, чем просто делить ручки на public и admin.

## 13. Что это означает для фронтенда

В едином `frontend/` должны появиться 2 слоя:

### Публичный white-label слой

- резолв клиники по домену или `clinic_slug`
- тема клиники
- страницы специалистов
- запись на прием

### Закрытый кабинетный слой

- кабинет администратора клиники
- кабинет врача
- кабинет call-центра
- кабинет sales
- кабинет пациента

## 14. Главный технический вывод

С точки зрения backend на `Go`, ядро решения должно строиться так:

1. роли и доступы делать через `role + scope`, а не только через строковые permissions по названиям клиник
2. white-label держать как конфигурацию клиники, а не как отдельные фронтенд-проекты
3. запись проектировать вокруг транзакций, слотов и snapshot данных пациента
4. различать сценарии анонимного, авторизованного, врачебного и операторского доступа уже на уровне API и service layer
