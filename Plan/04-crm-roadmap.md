# CRM roadmap

## Назначение CRM

`crm` должен стать операционным слоем клиники для работы с входящими заявками, повторными обращениями, задачами сотрудников и сопровождением пациента до и после записи.

Если `marketplace` отвечает за факт записи, то `crm` отвечает за путь пациента к этой записи и дальнейшую коммуникацию.

## Бизнес-цели

- не терять входящие заявки
- видеть источник каждого обращения
- управлять воронкой обработки
- ставить задачи администраторам и операторам
- связывать коммуникации с пациентом и записью

## Базовый scope CRM

### Лиды и заявки

Система должна хранить:

- входящие заявки с сайта
- звонки и ручные обращения
- повторные обращения существующих пациентов
- статус обработки заявки
- ответственного сотрудника

### Воронка

Минимальные стадии:

- `new`
- `in_progress`
- `contacted`
- `appointment_booked`
- `won`
- `lost`

### Задачи

Минимальные возможности:

- создать задачу
- назначить исполнителя
- задать дедлайн
- отметить выполнение
- связать задачу с лидом, пациентом или записью

### Коммуникации

Система должна позволять хранить:

- комментарии сотрудников
- историю звонков
- текстовые заметки
- факт отправки уведомлений

## Основные сущности

### `lead`

Первичное обращение пациента или представителя.

Поля первой версии:

- `id`
- `organization_id`
- `clinic_branch_id`
- `patient_id`
- `source`
- `status`
- `full_name`
- `phone`
- `email`
- `comment`
- `assigned_to_user_id`

### `pipeline_stage`

Справочник этапов воронки.

### `crm_task`

Задача сотрудника.

Поля первой версии:

- `id`
- `organization_id`
- `title`
- `description`
- `status`
- `priority`
- `assignee_user_id`
- `due_at`

### `communication_event`

Контакт с пациентом или лидом.

Поля первой версии:

- `id`
- `organization_id`
- `lead_id`
- `patient_id`
- `appointment_id`
- `channel`
- `direction`
- `summary`
- `performed_by_user_id`

## Интеграция с другими сервисами

### Связь с `marketplace`

`crm` должен получать или читать:

- `appointment_id`
- статус записи
- дату и время записи
- филиал и специалиста

На старте достаточно мягкой интеграции через HTTP API или события второго этапа.

### Связь с `auth`

`crm` использует:

- пользователей и роли
- permissions сотрудников
- организационный контекст доступа

### Связь с `mis`

На первом этапе интеграция может быть минимальной:

- ссылка на `patient_id`
- ссылка на завершенные приемы в будущем

## Роли и permission codes

Роли:

- `platform_admin`
- `clinic_admin`
- `registrar`
- `operator`
- `manager`

Пример permission codes:

- `crm.lead.read`
- `crm.lead.create`
- `crm.lead.update`
- `crm.pipeline.manage`
- `crm.task.read`
- `crm.task.manage`
- `crm.communication.read`
- `crm.communication.create`

## Frontend контур

Экраны CRM реализуются в **едином** корневом [`frontend/`](../frontend/) (маршруты вида `/crm/...`), данные — с `NUXT_PUBLIC_CRM_API_BASE`, авторизация через `auth`.

Первый UI-набор:

- список лидов
- kanban или tabular воронка
- карточка лида
- список задач
- мои задачи
- журнал коммуникаций

## Этапы развития CRM

### Этап 1

- лиды
- стадии воронки
- назначение ответственного
- базовые задачи

### Этап 2

- коммуникации и журнал касаний
- связка лида с записью
- автоматическое создание лида из внешних форм

### Этап 3

- отчеты по конверсии
- SLA по задачам
- триггерные напоминания и автоматизации

## Критерии готовности базового CRM-контура

- ни одна входящая заявка не теряется без статуса
- по каждой заявке виден ответственный
- сотрудник может создать задачу по пациенту или лиду
- лид можно довести до записи в `marketplace`
- клиника видит базовую конверсию по воронке
